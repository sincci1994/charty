> 작성 2026-08-24. **낡는 조건**: 상위 부채 5개 중 하나라도 상환되면, 또는 확장 시나리오(iOS·결제·경쟁 기능)
> 중 하나가 착수되면 갱신. 실측 근거는 [charty-web.md](charty-web.md).

## 1. 판정: 지금 구조는 잘 짜여 있는가

**결론: 그렇다 — 이 규모(1인 개발, TS ~5,280줄)에서 모범적인 편이다.** 근거:

- 의존 그래프가 거의 완벽한 단방향 트리 (types→lib순수→store→screens, 순환 1건뿐)
- 도메인 핵심(engine)이 UI 무결합 139줄로 격리, 테스트가 거기 집중
- 의존성 6개, 서버 코드 0, 배포 3타깃의 분기 코드 27줄 — 과잉 추상화 없음
- 부채 표기 규율: TODO 0건, 의도적 단순화는 전부 `ponytail:` 10건으로 천장·경로 명시

**"에이전트 작업으로 부채가 쌓이고 있나"에 대한 답**: 쌓이고 있으나 *기록되며* 쌓이고 있다.
위험한 부채는 표기 안 된 것인데, 전수 조사에서 표기 밖 부채는 5개로 특정됐다(아래 §2).
현 시점 리팩터링 대수술은 **불필요**하다 — 아래 5개를 기회 있을 때 상환하면 된다.

## 3. 확장 시나리오별 구조 진화 경로

원칙: **미리 만들지 않는다.** 각 시나리오가 실제 착수될 때 해당 최소 변화만.

### iOS (Capacitor) — 이미 계획됨 (Archives/2026-08-23 참조)
- 구조 영향 최소: `src/lib/native.ts` 신설(전역 Capacitor 감지 + OAuth 딥링크) + AuthButtons 1분기.
  이때 ④를 함께 상환하면 인증 진입점이 1곳이 된다.
- Apple 로그인 의무(스토어 규정 4.8) → provider 추가도 같은 진입점에.

### 수익화 (기간제 챌린지 결제 — docs/차티앱수익화방향.md)
- **서버 신뢰 경계가 처음으로 필요해지는 순간.** 결제·챌린지 판정을 클라이언트 상태로 두면 조작 가능.
- 처방: 전면 서버화가 아니라 **Supabase Edge Function 2~3개만** — ① 결제 웹훅 수신·검증 ② 챌린지 판정
  (records를 서버가 읽어 계산) ③ 필요 시 엔트리 잠금. 나머지 Local-first 구조는 그대로.
- 스토어 정책: 앱 내 디지털 상품은 Play 결제 15%~ / 웹 결제는 앱 내 유도 금지 — 결제 설계 때 재확인.

### 경쟁·리더보드류
- 위와 동일한 이유로 Edge Function 검증 필수 + records에 서버 타임스탬프 도입. 그 전까지는 만들지 말 것.

### 커스텀 도메인 (charty.app — 10월 초 드롭 감시 중)
- 코드 0줄: Vercel 도메인 추가 + Supabase URL 설정 + twa-manifest host 변경·재빌드. (Archives/2026-08-23 절차 참조)

### 기능 성장 (화면·지표 증가)
- 분해 트리거를 미리 정해둠: **화면 500줄 초과 시** 분해 (Simulation 455·Home 450이 경계 —
  분해선은 이미 명확: Simulation의 블라인드 필터·TF 컷오프→lib, Home의 자산차트·아바타·streak→컴포넌트).
  `data.ts`는 300줄 초과 시 상수/로더/포맷터 분리.
