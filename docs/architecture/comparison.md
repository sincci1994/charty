## 웹 전환 결정은 옳았는가 — 회고

**옳았다. 수치가 증명한다.** RN 스택은 인프라(인증·DB·API 8도메인)를 다 만든 시점에 제품이 0줄이었다.
웹 스택은 의존성 6개·서버 코드 0줄로 R16(시뮬 엔진, 행동 리포트, 기기 동기화, 재무 탭, AI 코치)까지 왔고,
같은 코드가 PWA→TWA(안드로이드)→Capacitor(iOS 예정)로 3플랫폼을 커버한다.

결정적이었던 구조적 선택 3가지:
1. **상태 소유권 역전** (서버→클라이언트) — 기능 하나 추가할 때 스키마·API·클라이언트 3곳이 아니라 1곳만 만진다.
   서버는 jsonb 덤 저장소라 스키마 변경이 배포를 막지 않는다.
2. **데이터를 API가 아니라 정적 CDN으로** — 요청당 비용 0, 캐싱 공짜, 파이프라인(fetch-data.py)만 지키면 됨.
3. **엔진을 순수 모듈로 격리** — UI 3벌(웹/TWA/Capacitor)이 같은 139줄을 공유하고, 테스트가 그 한 곳에 집중된다.

**대가로 받아들인 것** (몰랐던 게 아니라 선택): 서버 검증 부재(잔고 조작 가능 — 경쟁 기능 생기면 재검토),
LWW의 동시 기기 충돌(마지막 쓰기 승리), 오프라인 데이터 신선도(SW 캐시 폴백 수준).
이 한계들의 상환 시점은 [proposal.md](proposal.md)에.
